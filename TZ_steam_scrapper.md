# ТЗ: steam_scrapper — доведение до законченного MVP

## 0. Контекст

Репозиторий: `6killet/steam_scrapper`. Python, aiohttp, pydantic v2, SQLAlchemy 2 + aiosqlite.
Текущая структура: `sources/` (pricempire, steamwebapi, cs2sh), `services/` (collector, normalizer, scorer), `models/`, `storage/` (db, repositories), `output/` (console, csv_exporter), `config.py`, `main.py`, `items.txt`.

Сейчас это разовый batch-скрипт: читает items.txt → тянет цены из источников → нормализует → считает score → печатает топ + CSV + SQLite.

**Назначение системы:** скраппер — это read-only слой price intelligence. Он собирает данные, копит историю, анализирует и выдаёт сигналы. Он НЕ покупает, НЕ продаёт, НЕ логинится в Steam-аккаунты. Автотрейдинг — отдельная будущая система, не входит в это ТЗ.

## 1. Жёсткие ограничения (не нарушать)

1. Источники данных — ТОЛЬКО три существующих API: Pricempire, SteamWebAPI, cs2.sh. НЕ добавлять прямой скрейпинг steamcommunity.com, НЕ добавлять прокси-ротацию, user-agent пулы и т.п. — rate limits разруливаются вежливыми задержками и backoff на уровне этих трёх API.
2. НЕ добавлять Redis, RabbitMQ, Celery, Docker, MongoDB. Хранилище — SQLite. Планировщик — внутри одного Python-процесса.
3. НЕ добавлять никакой функциональности покупки/продажи/логина в Steam.
4. Сохранять текущую слоистую архитектуру (sources / services / models / storage / output). Новые модули добавлять в существующие слои.
5. Все денежные расчёты — `Decimal`, не `float`. На границах (JSON API, БД) конвертировать явно.
6. Конфигурация — через `.env` + pydantic settings (как сейчас). Все новые параметры добавить в `.env.example` с комментариями.
7. Каждый этап завершается работающим состоянием: проект запускается, тесты зелёные. Не начинать следующий этап с поломанным предыдущим.

## 2. Этап 1 — Режим демона и накопление истории

Самый приоритетный этап: исторические данные — актив, который копится только со временем.

### 2.1. CLI-режимы

Переделать `main.py` на subcommand-структуру (argparse достаточно):

- `python main.py scan` — текущее поведение: один проход, печать топа, CSV.
- `python main.py collect` — бесконечный цикл: проход сбора каждые `COLLECT_INTERVAL_MINUTES` (default 30), запись истории в БД, без печати топа. Graceful shutdown по Ctrl+C (даём текущему проходу дописаться или отменяем корректно через asyncio).
- `python main.py top` — построить и напечатать топ из последних данных в БД БЕЗ нового сбора.
- `python main.py bot` — запуск Telegram-бота (этап 5).

Планировщик — простой `asyncio`-цикл со sleep; APScheduler не нужен.

### 2.2. Схема истории в SQLite

Новые таблицы (SQLAlchemy-модели в `storage/`):

```
price_snapshots
  id, ts (UTC), market_hash_name, source (pricempire|steamwebapi|cs2sh),
  market (steam|buff|skinport|csfloat|waxpeer|...),
  price_type (sell_listing | buy_order | avg_24h | transaction),
  price (NUMERIC, в USD), currency_original, volume (nullable int)

sell_history_points   -- если какой-то из API отдаёт историю продаж
  id, market_hash_name, market, ts_point, price, amount

collect_runs          -- журнал проходов
  id, started_at, finished_at, items_requested, prices_saved, errors_json
```

Индексы: `(market_hash_name, ts)`, `(market_hash_name, market, price_type, ts)`.

Требование: каждый проход `collect` дописывает snapshot'ы, ничего не перезаписывая. Сырые JSON-ответы продолжать сохранять (raw), но добавить ротацию: хранить raw не дольше `RAW_RETENTION_DAYS` (default 14), чистить при старте прохода.

### 2.3. Расширение вселенной предметов

items.txt оставить как опциональный whitelist. Добавить режим `ITEMS_MODE=file|universe` (default `file`):

- `universe`: получить полный список market_hash_names из Pricempire (bulk-эндпоинт списка предметов CS2), отфильтровать по `MIN_PRICE_USD` / `MAX_PRICE_USD` (defaults 1 и 500), ограничить `UNIVERSE_MAX_ITEMS` (default 2000).
- Если задан items.txt и режим `file` — поведение как сейчас.

Уважать rate limits: батчинг запросов, задержки из конфига per-source, существующий exponential backoff сохранить.

### Критерии готовности этапа 1

- `collect` работает часами без падения; после двух проходов в `price_snapshots` есть записи с разными `ts` по одним и тем же предметам.
- Ошибки одного источника не валят проход (логируются, проход продолжается с остальными).
- `top` работает без сети.

### 3.2. Перерасчёт ROI в Scorer

Для каждого предмета считать ДВЕ метрики вместо одной (паттерн buff2steam):

- `roi_realistic` — от **buy order** Steam (мгновенный кэшаут): `(subtract_fee(steam_buy_order) - external_price) / external_price`.
- `roi_optimistic` — от **sell listing**: `(subtract_fee(steam_sell_listing) - external_price) / external_price`.

В score и в сортировку идёт `roi_realistic`. `roi_optimistic` — справочное поле в выводе. Если buy order по предмету недоступен ни из одного источника — предмет помечается `no_cashout_data` и в топ не попадает (показывается отдельной секцией «нет данных по выкупу» только при флаге `--show-incomplete`).

В модель `ScoredOpportunity` добавить поля: `roi_realistic`, `roi_optimistic`, `net_profit_usd` (абсолют после комиссии), `buy_market` (где покупать), `steam_buy_order`, `steam_sell_listing`.

### Критерии готовности этапа 2

- Тесты fee зелёные, включая ≤ $0.66.
- В выводе `scan`/`top` видны обе ROI-метрики; сортировка по realistic.

## 4. Этап 3 — Фильтры ликвидности

Модуль `services/filters.py`, применяется в Scorer до скоринга. Все пороги в конфиге:

1. `MIN_VOLUME_24H` (default 10) — минимум продаж за 24ч на Steam (из доступных полей API; если объём недоступен ни из одного источника — предмет отфильтровывается с причиной `no_volume_data`).
2. `MIN_BUY_ORDER_QTY` (default 3) — buy orders с количеством < 3 считать ненадёжными (паттерн SteamTradingSiteTracker: защита от фейковых/манипулятивных ордеров). Если API не отдаёт qty — фильтр пропускает, но ставит флаг `qty_unknown`.
3. `MIN_PRICE_USD` / `MAX_PRICE_USD` — ценовой коридор.
4. `MIN_SOURCES` (default 2) — цена подтверждена минимум двумя независимыми источниками; расхождение цены одного маркета между источниками > `MAX_SOURCE_DIVERGENCE_PCT` (default 15%) → флаг `divergent_data`, предмет в топ не идёт.

Каждый отфильтрованный предмет логируется с причиной (level DEBUG). В summary прохода — счётчики: сколько отсеяно каждым фильтром.

### Критерии готовности этапа 3

- В топе нет предметов без данных об объёме и без buy order.
- Summary показывает воронку: всего → после фильтров → в топ.

## 5. Этап 4 — Аналитика по накопленной истории

Активируется автоматически, когда по предмету в `price_snapshots` есть ≥ `STABILITY_MIN_DAYS` (default 7) дней данных. До этого score считается без компонента стабильности, предмет помечается `history_insufficient`.

### 5.1. `services/history_analyzer.py` — стабильность цены

Алгоритм из Soniclev/steam_csmoney (harmonic mean stability):

1. По истории transaction/avg-цен предмета построить скользящие окна по 15 точек.
2. Для каждого окна — взвешенное гармоническое среднее (`statistics.harmonic_mean(data=prices, weights=volumes)`); если volume отсутствует — невзвешенное.
3. Предмет «стабилен», если ВСЕ четыре условия:
   - CV = stdev(window_means) / median(window_means) < 0.06;
   - нет падающего тренда: не (первое среднее > последнего с отклонением > 1%);
   - min(means) не ниже медианы более чем на 10%;
   - max(means) не выше медианы более чем на 10%.
4. Результат: `is_stable: bool` + `stability_cv: float` — оба в `ScoredOpportunity`, `is_stable` входит в score с весом из конфига.

### 5.2. Рекомендация цены продажи (percentile sell suggestion)

Алгоритм `analyze_history()` из steam_csmoney:

1. По продажам за последние 7 дней построить обратную кумулятивную функцию: цена → процент продаж по цене НЕ НИЖЕ данной.
2. Целевой процентиль: P50 для предметов дешевле $100, P20 для дорогих.
3. Выдать `suggested_sell_price` — конкретную цену листинга. Добавить в вывод и в Telegram-карточку.

Если истории продаж нет (API не отдают) — строить по `transaction`/`avg_24h` snapshot'ам из собственной накопленной истории.

### 5.3. Приоритизация вывода — weighted_ratio

Для сортировки внутри топа (паттерн SteamTradingSiteTracker):
`weighted = buy_ratio * 0.4 + sell_ratio * 0.2 + trans_ratio * 0.4`, где ratio = внешняя цена / соответствующая Steam-цена. Использовать как вторичный ключ сортировки после score.

### 5.4. Мини-бэктест

`python main.py backtest --days N`: для каждого дня D в прошлом взять snapshot'ы на момент D, прогнать текущий Scorer, взять топ-K сигналов и посчитать, как изменилась цена этих предметов через `BACKTEST_HORIZON_DAYS` (default 7) по фактической истории. Вывод: средний/медианный исход топ-сигналов vs средний исход случайных предметов из той же выборки, win-rate. Без симуляции исполнения сделок — только сравнение цен. Это инструмент валидации скоринга, не торговый отчёт.

### Критерии готовности этапа 4

- На предмете с ≥ 7 днями истории появляются `is_stable`, `stability_cv`, `suggested_sell_price`.
- `backtest` отрабатывает на накопленной истории и печатает сравнение с baseline.

## 6. Этап 5 — Telegram-бот с UI

Библиотека: `python-telegram-bot >= 21` (async). Токен: `TELEGRAM_BOT_TOKEN` в `.env` — пользователь подставит свой, бот должен корректно сообщать об отсутствии/невалидности токена. Доступ: `TELEGRAM_ALLOWED_CHAT_IDS` (список через запятую) — сообщения от чужих chat_id игнорировать.

Запуск: `python main.py bot`. Бот и `collect`-цикл должны уметь работать в одном процессе: `python main.py bot --with-collect` поднимает оба (бот + фоновый сбор через `asyncio.create_task`).

### 6.1. Команды и UI (inline-кнопки)

- `/start` — приветствие + главное меню кнопками: [📊 Топ] [⚙️ Фильтры] [📈 Статус] [🔍 Поиск].
- `/top` (и кнопка «Топ») — топ-5 возможностей из последних данных БД. Каждый предмет — отдельная карточка:

```
🔫 AK-47 | Redline (FT)
Купить: Buff $8.40 → Steam buy order $10.20
ROI: +9.3% реал. / +14.1% оптим. | Профит: $0.78
Объём 24ч: 142 | Стабильность: ✅ CV 3.1%
Выставлять по: $11.05 (P50)
[Подробнее] [Steam ↗] [Buff ↗]
```

  Под списком — пагинация: [⬅️] [стр 1/4] [➡️] и [🔄 Обновить]. «Steam ↗» — URL на страницу предмета в Steam Market (формируется из market_hash_name, url-encode), «Buff ↗» и прочие — если источник дал ссылку/ID.
- «Подробнее» — расширенная карточка: цены по всем маркетам и источникам, история (мин/макс/медиана за 7д из своей БД), все флаги фильтров.
- `/filters` (и кнопка «Фильтры») — интерактивная настройка порогов кнопками: мин. ROI (5/10/15/20%), мин. объём 24ч (5/10/25/50), ценовой коридор. Выбор сохраняется per-chat в таблицу `bot_settings` и применяется к `/top` и к уведомлениям этого чата.
- `/status` — время последнего прохода collect, кол-во предметов/снапшотов, ошибки последнего прохода, размер БД.
- `/item <часть названия>` (и «Поиск») — поиск по подстроке в БД, до 5 совпадений кнопками, по нажатию — карточка предмета.

### 6.2. Авто-уведомления

После каждого прохода `collect`: предметы с `score`/`roi_realistic` выше порогов чата, прошедшие все фильтры, отправляются карточкой в каждый разрешённый чат. Антиспам:

- по одному предмету не чаще `NOTIFY_COOLDOWN_MINUTES` (default 360) — таблица `notifications_sent (chat_id, market_hash_name, last_sent_at)`;
- не более `NOTIFY_MAX_PER_RUN` (default 5) уведомлений за проход;
- повторное уведомление по тому же предмету — только если ROI вырос минимум на 2 п.п. с прошлого раза.

Кнопка [🔕 Не присылать этот предмет] на карточке уведомления — добавляет предмет в per-chat mute-список.

### Критерии готовности этапа 5

- Бот стартует с валидным токеном, меню/топ/фильтры/поиск работают, кнопки не падают на edge cases (пустая БД → человеческое сообщение «данных пока нет, запусти collect»).
- Уведомления приходят после прохода и уважают антиспам.
- Чужой chat_id не получает ответов.

## 7. Сквозные требования

1. **Тесты (pytest, pytest-asyncio):** fee-модуль (полное покрытие, см. этап 2), фильтры (таблица случаев), history_analyzer (синтетические серии: стабильная / падающая / с выбросом — проверка всех четырёх условий), percentile suggestion (известное распределение → известный ответ), нормализация валют. Для sources — тесты на парсинг сохранённых фикстур JSON (положить примеры ответов в `tests/fixtures/`). Сетевые вызовы в тестах — только моки.
2. **Логирование:** существующий формат сохранить; у каждого прохода — итоговая строка-summary (предметов, снапшотов, отфильтровано, ошибок, длительность).
3. **Документация:** обновить README (русский): установка, .env, все CLI-режимы, описание score-формулы и обеих ROI-метрик, схема таблиц. Обновить CLAUDE.md под новую структуру.
4. **Зависимости:** добавить в requirements.txt только `python-telegram-bot`; новых тяжёлых зависимостей (pandas, numpy и т.п.) не вводить — статистика на stdlib (`statistics`, `math`).
5. **Миграция схемы:** alembic не вводить; init_db создаёт недостающие таблицы; если структура существующих таблиц изменилась — задокументировать в README, что БД MVP можно пересоздать (`rm data/*.db`).
